Porting to 64-bit RISC OS: what actually bites

Every hazard below cost us real days. They are collected here so they cost you an afternoon's reading instead. Part one applies to anyone building 64-bit RISC OS code with the riscos64 toolchain; part two is Phoenix-specific; part three is how to work so these things surface early.

Written 13 September 2026 · updated 14 September · Phoenix RISC OS project · MIT
Everything here is measured on real hardware (Pi 4, CM4, Pi 5, CM5) unless explicitly marked as a hypothesis.

If you read one paragraph, read this one.

The 64-bit bugs that hurt are not the ones that fail to compile. They are the ones where a 32-bit convention changes meaning rather than changing syntax — so the code still builds, still links, still loads, and then quietly reads a register nobody wrote or a field four bytes past where it lives. A 32-bit assumption on a 64-bit build goes silent; it does not go loud. Nearly every entry in Part 1 is a variation on that one sentence.

Part oneThe 64-bit hazards

These apply to any 64-bit RISC OS work — gerph's riscos64 toolchain, the build service, your own modules. None of them is Phoenix-specific.

1. A -1 sentinel written as 0xFFFFFFFF does not survivecrashes

Symptom: instant data abort and reset, no error, nothing in the log. Often on a Pi 5 and not elsewhere.

_kernel_swi_reg is int32_t — signed. A caller passing −1 gives r[n] == -1, and casting that to a pointer sign-extends:

(Wimp_Window *)regs->r[1]      ->  0xFFFFFFFFFFFFFFFF
((void*)(0xFFFFFFFFul))        ->  0x00000000FFFFFFFF    NEVER MATCHES

The comparison fails silently, the "no buffer / read size only / not supplied" branch is skipped, and the bogus pointer is used as a real address. In WimpTemplates that was a 16-byte store to 0xFFFFFFFFFFFFFFFF.

At 32 bits both sides are 0xFFFFFFFF and the code is correct — which is exactly why these survive for years in well-tested modules.

The fix is the sentinel, not the cast:

#define READ_SIZE ((void*)-1)   /* 0xFFFFFFFF at 32-bit, all-ones at 64 */
How to find them 
grep -rn "0xFFFFFFFF" --include="c/*" --include="h/*" | grep -i "void\s*\*\|(.*\*)"

and treat every -Wint-to-pointer-cast warning as a candidate — the compiler names the exact line. Ours had been doing so in every build we had ever run:

swis_template.c:204: warning: cast to pointer from integer of different size
  204 |   Wimp_Window * window = (Wimp_Window *)regs->r[1];

2. Flags do not reach a C caller — so flag-based results vanishsilent

Symptom: nothing. Truncated data, a loop that never runs, a limit nobody knew was there.

OS_GSTrans reports a full output buffer by setting Carry. Correct, documented, and on AArch64 useless: Carry does not reach a C caller through _swix. riscos64 therefore signals GSTrans overflow by returning R1 = 0, and gerph's SystemVars checks exactly that:

err = _swix(OS_GSTrans, _INR(0,2)|_OUTR(1,2), s, output,
            size_and_flags, &is_valid, wrotep);
if (err == NULL && !is_valid) err = err_BufferOverflow;

Phoenix set the Carry and never touched R1, which still held the incoming buffer pointer — non-zero, so is_valid was always true. SystemVars never saw an overflow, its realloc loop never ran, and every system variable was silently truncated at 16 bytes, on every board, for the life of the implementation.

It surfaced only because Font$Path is 25 characters and was the first long variable the project ever set. Sys$Time is 8, Sys$Date 10, Sys$Year 4. A 16-byte ceiling is invisible until something crosses it.

The general trap

When an interface is ported from 32 to 64 bits, the signal that moved does not fail loudly — the old one is simply never read. No error, no warning, no "unsupported": the caller reads a register you never wrote and believes whatever was already in it.

If you implement a SWI that reports anything via flags, go and read what the 64-bit callers actually check. Same family as _OUT(_FLAGS). We now signal both — Carry for 32-bit callers, R1 = 0 for 64-bit ones.

3. Two structs aliased onto each other: LP64 pads one and not the othersilent

Symptom: a pointer field reads as NULL, or as small non-null garbage — and which one you get depends on the address.

MessageTrans handed its internal view of a message file to callers by aliasing the caller's control block rather than copying it:

*mfdp = (messagefiledata_t *)&cb->size;
struct MessageTrans_ControlBlock {    struct messagefiledata_s {
    uint32_t magic;        // 0            int32_t        size;        // 0
    uint32_t size;         // 4            messagefile_t *messagefile; // 8
    void *   messagefile;  // 8        };
};

From &cb->size the fields sit at +0 and +4. messagefiledata_t puts the pointer at +8, because LP64 needs 8-byte pointer alignment and the compiler inserts padding after the int32_t. The aliased view reads four bytes past the real pointer. It broke every MessageTrans lookup on a 64-bit build. On 32-bit both are {u32, ptr} with no padding, the alias is exact, and this cannot be seen.

One bug, two faces — and the face depends on where memory is

Little-endian, reading eight bytes four past a pointer picks up that pointer's high word as the low word of the result. So the symptom depends entirely on how high the address was:

Where the data livedHigh wordReads asSymptom
Phoenix RMA, 0x026F76980NULLwalks into the scan and hangs
Linux host, 0xb3d9ff6954900xb3d90xb3d9non-null garbage, instant segfault

Two completely different-looking failures, one cause. Had we only ever seen the hang we would have hunted a loop bug; only the segfault, a corrupt allocation. A symptom that changes shape with the address is a layout fault until proven otherwise.

The general trap

Aliasing two struct definitions is a promise about layout that the compiler is under no obligation to keep, and padding is where it breaks first. A copy is a few instructions and cannot go wrong this way. If you genuinely want an alias, the two types must share one definition or carry a _Static_assert on the offsets.

4. A pointer inside a struct silently resizes an external file formatsilent

Draw_PathElement went 28 → 32 bytes because a continuation pointer shared a union with the coordinates. No error, no crash, wrong pixels — and the module size did not move a single byte, so nothing in the build output hinted at it.

The same shape appears wherever a struct describes something defined outside your program: a file format, a wire protocol, an OS block. Related: hook fields declared uint32_t are too narrow for an A64 pointer (we hit this in VideoV's vector path).

Rule

Guard every externally-defined layout with a compile-time sizeof assertion, and ask the binary its layout rather than reading the header and believing yourself. Note that char check[(cond)] is not a compile-time assertion under gcc — it looks protective and does nothing. Use _Static_assert.

5. Alignment: your platform may not be telling youphoenix-specific risk

Credit where due — this one we only checked because of Andrew Youll's excellent DEBUGGING.md in adyoull/desklib32, written from porting !RDPClient to 32-bit Norcroft. He notes RISC OS 5 defaults CPU alignment checking on, which is how he found four separate bugs.

What unaligned access actually does on AArch64:

ContextUnaligned load/store
Normal memory, SCTLR_EL1.A = 0Permitted, returns the correct value. No ARM32-style rotate.
Device memory (MMIO)Faults regardless of A
Pre-MMU (all memory behaves as Device-nGnRnE)Faults regardless of A
Exclusives (LDXR/STXR), atomicsFault regardless of A

Phoenix has never set SCTLR_EL1.A. So it never alignment-faults on ordinary RAM — but the Device and pre-MMU rows have bitten us five times, and the fixes are in our source as comments. The classic: -O2 merged eight byte reads into one ldur, which faulted pre-MMU and hung the boot silently, because pre-MMU the abort handler isn't installed yet. Fix is a volatile byte pointer, forcing individual ldrb.

Why this matters to you, not just to us

A machine that does not check alignment cannot tell you your port is clean. If you test on Phoenix and it passes with checking off, that is not evidence it will pass on RISC OS 5 with alignment exceptions on.

Update, 14 September — we turned it on, and it found three things. Phoenix now has *AlignCheck: On, Off, Test (one deliberate fault, to prove the check fires and can be reported) and Survey (log and skip rather than halt, so one boot yields the whole list). Default off, for a reason given below.

Two of the three were ours, and both had been invisible since the project started:

  • Our allocator misaligned half of every allocation. need = ALIGN_UP(hdr) + ALIGN_UP(size) + sizeof(uint32_t) — two aligned terms and a bare +4 for a tail canary, so need came out 4 mod 16 and every split shifted the next block by 4. Every struct, workspace and buffer in the kernel, and nothing ever failed, because with A clear the misaligned reads returned correct values.
  • gcc was merging narrow stores into wide unaligned ones — two adjacent 32-bit zero-stores became one 64-bit store at +4, on a properly aligned struct. Nothing had told it not to. -mstrict-align fixes the class.

With both fixed, Phoenix's kernel is alignment-clean: zero faults across its filing-system, font and module tests with the check confirmed armed, on two boards.

The third one is yours too, if you build with riscos64

The first application we tested took six faults inside __RelocCode — the self-relocation stub that every riscos64 binary carries. Its four 64-bit parameter words sat at 4 mod 8, because riscos64-mkreloc emits .balign 4 and then places .dwords after an arbitrary number of 4-byte instructions.

Whether it bites you is parity. The stub's length varies with what your image needs — no relocations and no GOT emits just RET; relocations add a block; a GOT adds another. The data lands misaligned only when the instruction count comes out odd. So with checking on you would see some binaries run and others die, with no pattern visible from outside. When we generated the stub in isolation to test the fix, it came out correctly aligned by luck — we had to remove one instruction to reproduce the failure.

The fix is two .balign 8 lines. We have rebuilt a real application with it and confirmed on hardware that the faults are gone, and it has gone upstream.

And why the default stays off. Once that stub was fixed, the same application faulted deeper in — at mod8=7, seven bytes past an 8-boundary, in a workspace it clears with 64-bit stores. No allocator produces that: it is an interpreter placing values at their natural byte offsets. That is a design choice, not a defect, and nobody can patch it from outside.

So a runtime toggle is not a compromise, it is the correct answer: there is real software that legitimately needs checking off. Turn it on to test your own code; leave it off to run everyone else's.

Meanwhile: avoid -Otime / aggressive optimisation on code that parses byte streams, and do not write parse macros as *(uint16*)p. Both encourage the compiler to fold narrow reads into wide unaligned ones.

6. .rodata pointer tables come back +8toolchain, open

Symptom: strings in a module print as the next string in the table.

A module relocates itself: __RelocCode computes its own delta with ADR and patches the words listed in __RelocData. Measured on FanController, comparing every table entry against what the linker had already written:

Target sectionEntriesTable minus section
.rodata36+8 — wrong
.bss40
.text20

.text/.bss being exact is positive proof the load address and delta are right. It is a constant +8 on the pointer value, not an indexing error — it merely resembles "the next entry" because the strings happen to be 8-byte aligned: "Manual" at 0x8f80 is patched to 0x8f88, which is "Managed". A module with no .rodata-targeted relocations is flawless, which is the predictive test and explains why some modules garble strings and others don't.

The defect is proven; the cause is a hypothesis — most likely riscos64-mkreloc fed from the Makefile's ld -r partial link, which concatenates .rodata.str1.8 while the final link merges duplicate strings. Reported upstream.

Workaround: use 2D char arrays (char msg[16] inside the struct) so there is no pointer to relocate.

7. Toolchain gaps worth knowing before you plan around them

  • CMunge 0.84 -64bit has no start code for module-is-runnable: — Serious Error: Start code not implemented for RISC OS 64 bit module. A real gap, not your CMHG. It is what "blocked on CMunge start-code" has always meant. Workable with a hand-written s/veneer64.
  • libAsm is 32-bit only, and muldiv's reason to exist expires on AArch64. But _callx already exists in the 64-bit CLib — we recorded it as a blocker needing "a ~40-line AArch64 veneer" that had in fact been written the previous October. Before recording something as a blocker, check whether it is already solved.
  • Pulling a library clone updates the source you READ, not the tools you RUN. riscos64-cc is an image wrapper carrying its own copies of the linker scripts and mkreloc. We updated a clone 0.28→0.31 and none of it reached our builds.
  • %p printed only the low 32 bits in the clib version we were on — in the very module whose 32-bit sentinel crashed a Pi 5. Print addresses at the width they are.

8. RISC OS build-system traps that look like missing files

  • The dot is a DIRECTORY SEPARATOR. riscos-amu -f Makefile.build64 → makefile/build64: would not open. Not missing — read as directory makefile, leaf build64. Never put a dot in a makefile name; put the suffix on the stem (MakefileBuild64,fe1). The ,fe1 is a filetype, not an extension, and is fine.
  • "Missing header" is an export-tree PATH, not an absence. #include "Global/ModHand.h" maps to Global/h/ModHand on disc — which is how the ROOL export tree is already laid out. Do not rename to the gcc layout; that breaks resolution that already worked. Simplest fix: put the tree inside the component, structure intact, and leave INCLUDES empty.
  • Never write stub Global headers. NewErrors is 119 KB of allocated error numbers. A stub either fails to compile or invents numbers, giving a module that builds, loads, and returns wrong error and reason codes with no symptom anywhere near the cause.
  • Changing a -D flag rebuilds nothing. Clean first, and verify the flag actually arrived. Worse, CModule feeds CDEFINES to CMunge as well as to cc, so a compiler code-generation flag put there never reaches the compiler and the rebuild silently tests nothing.

Part twoWorking on Phoenix

Phoenix is a bare-metal AArch64 RISC-OS-compatible kernel for the Raspberry Pi 4, CM4, Pi 5 and CM5. It is MIT licensed. It boots to a real * supervisor, runs BASIC, reads FileCore discs off NVMe/USB/SD, does networking and NTP, and loads real 64-bit RISC OS modules from disc.

One source tree, two builds — and the split is narrower than you'd think

Phoenix was for a while genuinely one binary: a single kernel8.img booted Pi 4, CM4 and Pi 5 unmodified, because the device-tree HAL detected the board at runtime. That is no longer strictly true, and it is worth knowing exactly how far it has drifted, because most of the design still works the old way.

Two things now differ between the images:

What divergesScope
-mcpu=cortex-a72 vs -mcpu=cortex-a76 The whole tree. Codegen only — this is what makes the two images differ in most of their bytes.
-DPI_MODEL=4 / =5 Five sites, in two files. drivers/gpu/hdmi_audio.c — the BCM2712 HDMI audio driver is compiled in only on Pi 5, with stubs elsewhere. drivers/mmc/mmc.c — the SD host base is a fixed BCM2712 address on Pi 5, versus peripheral_base + EMMC2_OFFSET derived from the DT on Pi 4.

That is the entire compile-time board split. Everything else is still resolved at runtime from the device tree — peripheral base, GIC, memory, CPU count, and which USB path to take (RP1 xHCI on Pi 5, VL805 xHCI on Pi 4, DWC2 on CM4). The rule there is probe, do not match: periph_base tests a timer register rather than recognising a board string, which is why an Argon One CM5 — hardware nobody here had seen — worked first time.

So the accurate description today is one source tree, two board-specific images, with a narrow and deliberate set of compile-time exceptions. If you are adding board-specific code, the DT-HAL is still the default answer; a #if PI_MODEL should be a considered decision, not a reflex.

Deliberate constraint

Phoenix stays MIT and does not absorb GPL or unclear-licence code. Where we need third-party functionality it ships as its own module with its own licence, and we re-derive from device trees, datasheets and published specifications rather than copying. If you contribute, please keep to that — and note that a licence finding has a date on it. Re-check before relying on one; we have been caught out in both directions.

Building

make BOARD=pi4      # Raspberry Pi 4 / CM4 (cortex-a72)
make BOARD=pi5      # Raspberry Pi 5 / CM5 (cortex-a76)
The first thing that will trip you

Flash kernel8-pi4.img or kernel8-pi5.img — never kernel8.img, never phoenix64.img. Both of those are whichever board was built last and tell you nothing. phoenix64.img is the Makefile's TARGET and is written by every build whatever BOARD= says; its name suggests "the 64-bit build", which is the trap.

After a pi5 then pi4 build, all three of kernel8.img, phoenix64.img and kernel8-pi4.img are byte-identical Pi 4 kernels. Always produce both board images, and verify they differ (md5sum).

Every build stamps itself, and you should quote it

The boot banner prints a build stamp so every log self-identifies. This exists because three separate times in one evening a test ran against the wrong binary — a CM5 booting a day-old kernel, a stale module still on the disc, an SD-card overwrite prompt never answered. Every conclusion from those runs was worthless, and one nearly produced a per-board "fix" for a bug that did not exist.

Check the stamp before believing any result. And note that module size is not a tell — the Draw layout fix changed behaviour completely and moved the size not one byte. Disassemble, or diff the md5.

House rules
  • Touch sources, never object files. If the hardware disagrees with the source, suspect the binary you flashed first.
  • Add a GOTCHAS entry the same session you find the trap — and delete entries that stop being true. A rule the next commit quietly exempts itself from is worse than no rule.
  • Never put Phoenix on the only bootable device you own.
  • The CM5 has no serial capture. Screen output, or it did not happen.

Part threeMethod — how these were actually found

This part is opinionated and it is the half we would most want a new contributor to read. Every rule here is written because we broke it and paid.

Find the host runner before anything that needs hardware

Three test suites in this project needed only a C compiler and had never been run. One of them scored 1101/1420 and identified a real defect the first time it executed. Another found a bug hiding in its own warnings.

Do not grep for test — grep for a host compiler. Look for testcode/, tests/, Test/, verification/, .robuild.yaml, any Makefile mentioning gcc or cc rather than the cross-toolchain.

Related and separate: run the tests that ship with any module you did not write. MessageTrans came with 22 tests covering every SWI we had been guessing at. We had to be told twice.

Run it; don't read it

Reading source produces hypotheses. Running it produces answers. Five wrong theories about the MessageTrans fault died in about two minutes once the code was in a host harness. Much RISC OS module code is pure C and will compile and run on a Linux host with a small shim.

Two conditions on harnesses, both learned the hard way

1. EXTRACT the code, never retype it. We once "proved" a fix in a harness the kernel never received, and shipped a change that broke every newline in the system. Our harness scripts now sed the real functions straight out of the real source file, so the thing under test and the thing that ships cannot diverge.

2. Check that the test discriminates. Reinstate the bug and confirm the test fails. A test that passes against both the broken and the fixed code is measuring nothing — and it will read as reassurance forever.

Your own instrument is the first suspect

Four separate striking findings in this project came from diagnostics we had just added, and all four were wrong. A confident verdict from a new instrument is its least trustworthy output.

Concretely: our con_printf handles only %s %d %u %x %c, and an unknown conversion consumes no argument, shifting every column after it. That faked a bug for two days. And a serial capture that drops ~14% of lines under load faked a board-dependent bug for another two.

Absence from a log is not evidence of absence. Count inside the program and print the total.

Use an existing trusted path as the oracle, not a fixture

The best test we wrote this month proves a new filing-system dispatch layer by reading the same file two ways and enumerating the same directory two ways — new path against the long-trusted one. It cannot pass while being wrong, and it needs no golden values.

The payoff was visible immediately: enumeration returned 20 names on the Pi 4 and 22 on the Pi 5 — different discs, each agreeing with itself. A hardcoded expected value would have been wrong on one of the two boards and we would have "fixed" a working implementation to match it.

A workaround that makes the test pass deletes the evidence

Our mouse Y axis was inverted on every board for months. It survived because the "known-good decoder" proof only ever checked X. Making a symptom go away is not the same as understanding it, and it destroys the thing you would have needed to understand it later.

Two smaller ones that keep recurring

  • Two bugs can each disprove the other. When fix after fix changes nothing, that is data — consider that you have two faults stacked, each acting as a false negative for the other. We had exactly this in CM5 WiFi.
  • A probable answer stated as a known one is still a wrong attribution. Say which parts are measured and which are inferred. Most of the entries above distinguish the two, and where we could not, we said so.

Open question32-bit Wimp blocks at LP64 — we would like your view

This is the one we have not solved, and it blocks more than it looks.

A Wimp window block is a fixed run of 32-bit words defined by the OS. A C struct describing it doubles the moment it contains a pointer — so every Wimp library's window, icon and template structs are wrong at LP64, in the same way but not necessarily by the same amount.

Andrew Youll hit the small version of this from the 32-bit Norcroft side: a group of unsigned int : 1 bitfields pushed DeskLib's wimp_colourflags from 8 bytes to 12 and shifted every field after it, so template loading requested a bogus allocation and the application died on launch. We hit the large version from the 64-bit GCC side. Two people, opposite directions, same wall.

It currently blocks a WindowScroll port for us, makes riscos64-oslib's structs unusable at LP64, and stands between the community and a 64-bit DeskLib.

Why we are asking rather than deciding

Whoever answers this first sets a convention. If several projects each solve it privately, we end up with incompatible conventions in different libraries, which is materially worse than the current situation of none. We would much rather it were settled once, in the open, by the people who maintain these libraries — and then DeskLib, OSLib, RISC_OSLib and the rest become largely mechanical conversions.

If you have a view, or you have already solved it in your own code, we would genuinely like to hear it.

Corrections welcome, and expected. Several entries here contradict what this project itself wrote earlier — the .rodata relocation cause and the alignment framing were both stated confidently and wrongly the first time, and "one binary, all boards" was corrected within a day of publication. Part 1 §5 has been rewritten since: what was an open defect we were "leaning towards" fixing is now three located bugs, two fixed in our own code and one fixed upstream. If something here is wrong, or is right but out of date, please say so; a bulletin nobody corrects is a bulletin nobody is reading.
